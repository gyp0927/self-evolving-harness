## Task

解决外部API调用可能因网络波动、服务过载或配置错误而超时失败的问题。核心目标不是“保证成功”，而是“保证有结果”——要么成功获取数据，要么快速降级返回可用替代方案，避免无意义的长时间重试和资源浪费。

## Procedure

1. **前置健康检查**：在发起正式请求前，先执行轻量探测（如HEAD请求、ping或连接测试），设置短超时（2s）。若探测失败，直接进入降级流程（步骤5），不浪费正式请求的重试次数。

2. **分级超时设置**：根据请求类型配置差异化超时——快速失败类请求（如状态查询）使用短超时（2-3s），关键数据请求（如订单详情）使用长超时（8-10s）。避免一刀切策略导致快速请求被拖慢或关键请求过早放弃。

3. **动态重试机制**：每次失败后，根据失败类型和连续失败次数计算退避时间：
   - 连接超时（网络层问题）：可重试，退避时间 = 基础时间(1s) × 2^重试次数 + 随机抖动(0-500ms)
   - 响应超时（服务端可能过载）：需更长退避，退避时间 = 基础时间(3s) × 2^重试次数 + 随机抖动(0-1s)
   - 设置最大重试上限（max_retries=3），达到上限后停止重试，进入熔断评估

4. **熔断器状态管理**：维护熔断器状态机（关闭→打开→半开）：
   - 连续失败达到阈值（如3次）→ 熔断器打开，后续请求直接走降级路径
   - 熔断打开后，定期（如30s）尝试半开探测——放行1个测试请求，成功则关闭熔断器，失败则继续保持打开
   - 熔断期间不发起真实业务请求，避免对已过载服务造成更大压力

5. **降级策略执行**：当熔断器打开或重试全部失败时，按优先级依次尝试：
   - 备用API：调用配置的备用服务商接口
   - 缓存数据：返回最近一次成功获取的缓存结果（标注数据时间戳）
   - 默认值：返回业务可接受的默认数据或空结构，确保调用方不阻塞

6. **全程日志记录**：记录每次尝试的时间戳、超时类型、退避时长、重试次数、熔断状态变化、降级路径及最终结果。日志用于事后复盘和策略调优，量化分析超时模式和服务可用性趋势。

## Lessons

- **前置检查是性价比最高的防护**：一次2s的轻量探测能避免4次正式请求（每次可能耗时10s+）的无效消耗，在系统不可用时将总耗时从分钟级降至秒级。
- **静态重试策略是最大的坑**：固定间隔重试在瞬时故障时有效，但在服务过载时反而加剧拥塞。必须根据失败类型动态调整退避时间——连接超时是网络问题可快速重试，响应超时是服务端问题需更长等待。
- **熔断器比无限重试更可靠**：连续失败说明服务可能已不可用，继续重试只是浪费资源。熔断器打开后直接降级，配合半开探测实现自动恢复，既保护了调用方也保护了被调服务。
- **“保证成功”是错误目标**：在分布式系统中，任何外部依赖都可能失败。正确的目标是“保证有结果”——通过降级路径（备用API/缓存/默认值）确保业务不中断，比执着于重试成功更有价值。
- **退避时间要舍得给够**：总耗时7.56s、平均每次等待不足1s的重试策略，对真正的超时场景（如服务过载持续30s+）毫无意义。基础退避时间应参考历史P99响应时间，确保重试间隔大于服务恢复所需时间。
- **日志是策略调优的唯一依据**：没有完整的超时类型、退避时长、熔断状态记录，就无法判断策略是否有效。每次调用都要留下可量化的痕迹，才能持续优化重试参数和降级优先级。

## Update v2 (2026-08-18)

任务: 调用可能超时的API并保证成功

- - 明确设定了重试上限（4次）和退避策略（指数退避），避免了无限重试导致的资源浪费。
- - 每次重试前有等待间隔，防止对下游服务造成瞬时压力。
- - 最终如实报告失败结果（success=False），没有虚报成功，保证了结果的可信度。
- - **前置检查缺失**：策略中明确pre_check=False，导致4次正式请求全部浪费在注定失败的连接上。如果先做一次2秒的轻量探测，可以提前识别服务不可用，节省约5.5秒的无效重试时间。
- - **重试策略过于机械**：连续4次超时说明服务可能已宕机或网络完全中断，此时应触发熔断（如快速失败）或切换备用端点，而不是继续按固定次数重试。
- - **未利用已有技能**：参考技能中明确提到“前置健康检查”和“熔断降级”，但实际执行完全忽略了这两步，导致策略与技能脱节。
- - **耗时失控**：7.52秒的总耗时远超合理范围（若前置检查2秒+1次正式请求2秒=4秒内可完成），说明重试参数（如超时时间）未针对实际场景优化。
- - **阶段1：前置探测**（新增）→ 发送HEAD/连接测试，超时2s。若失败，直接进入降级流程（返回缓存/备用数据/明确报错），不发起正式请求。
- - **阶段2：正式请求**（保留）→ 设置合理超时（如3s），携带唯一请求ID便于追踪。
- - **阶段3：动态重试**（优化）→ 首次失败后，根据错误类型决策：
- - 超时/网络错误：指数退避（1s, 2s, 4s），但最多重试2次。
- - 5xx错误：退避后重试1次。
- - 4xx错误：不重试，直接失败。
- - **阶段4：熔断降级**（新增）→ 若连续2次超时，立即熔断（暂停后续重试），尝试备用API端点或返回降级结果（如缓存数据）。
- - **阶段5：结果上报**（保留）→ 无论成败，记录重试次数、耗时、错误类型，供后续策略优化。
- - **resilient-api-call-v3**：在v2基础上强制加入前置健康检查（默认开启），将重试策略改为“动态决策”（区分超时/5xx/4xx），并增加熔断阈值（如连续2次超时即切换备用端点）。同时增加“快速失败”模式：当总耗时超过预设预算（如5s）时，立即终止重试并返回降级结果。
