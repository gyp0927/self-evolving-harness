## Task

解决外部API调用可能因网络抖动、服务不可用、认证失效或请求过大等原因导致超时，进而引发任务失败的问题。本技能提供一套标准化的调用流程，确保在各类异常场景下，调用要么成功，要么以可控的方式降级，绝不无限重试或盲目失败。

## Procedure

1. **调用前检查（Pre-flight Checks）**
   - 若API提供健康检查端点（如 `/health` 或 `/status`），先调用并确认返回200。
   - 检查网络连通性：使用 `ping` 或 `nc -zv <host> <port>` 验证目标主机可达。
   - 确认认证凭据（API Key / Token）未过期，必要时提前刷新。
   - 估算请求体大小，若超过API限制（如10MB），先压缩或分片。

2. **设置分级超时（Graded Timeouts）**
   - 将超时拆分为两个独立阈值：
     - **连接超时**：2秒（用于定位网络层问题）。
     - **响应超时**：5秒（用于定位服务处理问题）。
   - 在HTTP客户端中分别配置 `connect_timeout` 和 `read_timeout`，禁止使用单一超时值。

3. **动态重试策略（Dynamic Retry Strategy）**
   - 首次调用失败后，根据错误类型决策，而非盲目重试：
     - **网络抖动 / 瞬时错误**（如 `ConnectionResetError`、`TimeoutError`）→ 采用指数退避重试，最多3次（间隔1s、2s、4s）。
     - **4xx / 认证错误**（如 `401 Unauthorized`、`403 Forbidden`、`429 Too Many Requests`）→ 立即停止，不重试，直接进入降级流程。
     - **5xx / 服务不可用**（如 `503 Service Unavailable`、`500 Internal Server Error`）→ 不重试，直接切换备用API或降级方案。
   - 每次重试前，重新检查步骤1中的前置条件（尤其是认证token是否在等待期间过期）。

4. **熔断与降级（Circuit Breaker & Fallback）**
   - 设定熔断阈值：**连续2次超时**（无论重试与否）即触发熔断，暂停对主API的后续调用。
   - 熔断后按优先级尝试以下降级方案：
     1. **备用API**：若存在同功能备用服务，切换过去并重复步骤1-3。
     2. **缓存数据**：若调用是读操作，返回最近一次成功的缓存结果（标注数据新鲜度）。
     3. **默认值**：若以上均不可用，返回业务可接受的默认值（如空列表、0值），并标记结果来源为“降级”。
   - 熔断状态持续30秒后自动半开，允许试探性请求；若成功则关闭熔断，若失败则重新开启。

5. **全程日志（Comprehensive Logging）**
   - 对每次调用（包括重试和降级）记录以下字段：
     - 时间戳（精确到毫秒）
     - 调用阶段（前置检查、连接、响应、重试、降级）
     - 耗时（连接耗时、响应耗时、总耗时）
     - 错误码（HTTP状态码或异常类型）
     - 请求ID（若API返回）或客户端生成的追踪ID
     - 重试次数
     - 最终结果（成功/失败/降级）及结果来源
   - 日志输出到结构化格式（如JSON），便于后续聚合分析。

6. **最终兜底（Final Fallback）**
   - 若所有重试和降级方案均失败，则：
     - 将任务标记为“部分成功”或“失败”，并附上完整错误日志。
     - 将失败详情写入死信队列（Dead Letter Queue）或错误报告系统，供人工介入。
     - 返回一个明确的错误响应给调用方，包含错误码和可读的错误信息，绝不静默吞掉异常。

## Lessons

- **固定重试+指数退避并非万能**：它只适用于瞬时网络抖动。面对持续超时（如API宕机、认证失效），重试只会浪费时间和资源。必须根据错误类型动态决策。
- **前置检查能避免大量无效调用**：健康检查、token过期检查、请求体大小估算，这三项能在发起正式请求前拦截大部分可预见的失败，成本极低但收益显著。
- **分级超时是定位问题的关键**：连接超时和响应超时混在一起时，无法判断瓶颈在网络层还是服务层。分开设置后，2秒内失败是网络问题，5秒后失败是服务处理问题。
- **熔断机制保护的不只是本次任务**：连续失败后继续调用，会加剧API服务端的负载，甚至引发雪崩。熔断后切换备用方案，既保护了自身任务，也避免了对下游的二次伤害。
- **失败详情必须记录**：没有错误码、耗时、请求ID的失败日志，事后复盘时只能靠猜。结构化日志是根因分析的唯一依据。
- **降级不是失败**：返回缓存数据或默认值，在业务上往往优于直接报错。关键在于明确标注结果来源，让调用方知道数据不是实时的。
- **绝不无限重试**：每一次重试都有成本（时间、资源、下游压力）。设定明确的重试上限（如3次）和熔断阈值（如2次连续失败），是工程纪律的体现。
